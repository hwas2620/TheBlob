# 원형질체 코어 — 0단계 관문 A 구현 계획

> spec: [spec.md](./spec.md) — "0단계 — 브라우저 프로토타입"의 관문 A (A0~A3)

## 사용자 결정 (2026-11-15)

- **`main` 병합은 주 세션이 한다.** 구현과 검증이 끝나면 작업 브랜치를 `--no-ff` 로 병합해 푸시한다.
- **속도는 최대한 빠르게.** A3 를 "프레임 4ms 를 넘는가"가 아니라 "프레임 4ms 안에서 화면 속도(초당 모델 시간)를 얼마나 낼 수 있는가"로 바꾼다.
  드로콜과 채우기 비용을 줄이는 수단을 처음부터 넣고(Step 7), 시간 간격을 키울 수 있는지도 numpy 로 본다(Step 7b).

## 범위

관문 A는 "풀이와 비용"이다. 목표 모델의 규칙 1~7(위상, 쉬는 두께, 압력, 유량, 강화, 마름, 젖음)과 멀티그리드 풀이를 WebGL2로 옮겨
게임과 분리된 디버그 페이지에서 돌리고, numpy 기준 실행과 견줘 맞는지 확인한 뒤 스텝당 비용을 잰다.

| 넣는 것 | 넣지 않는 것 (관문 B 이후) |
|---|---|
| 규칙 1~7, 토러스 격자, 유인장(굶은 이주 시험용) | 규칙 8(먹이 덩어리, 섭취), 점 먹이 |
| 멀티그리드 V(2,2), 스텝당 2사이클과 3사이클 | 입자층, 게임 연결, 본 렌더링 |
| 위상 무늬 (나) 삼각 격자 (끄고 켤 수 있게. 좌표와 시간의 함수라 셰이더 몇 줄) | 위상 무늬 (가) 수축파 (무게중심 축소 패스가 필요) |
| 확인용 단순 표시(두께와 정맥) | 정맥 그래프 판정(B3, B5) |

A1·A2가 "통합 모델"을 요구하므로 풀이만 따로 옮기지 않는다. 여기서 만든 코어는 관문 B와 1단계에서 그대로 쓴다.

## 설계

### 상태 텍스처 (N×N, RGBA32F, 핑퐁은 두 장씩)

| 텍스처 | 채널 | 비고 |
|---|---|---|
| `cellA` (핑퐁) | h, wet, age, sage | |
| `cellB` (핑퐁) | θ, slime, p, 직전 스텝의 p | p 는 풀이의 웜스타트와 외삽에 쓴다 |
| `edgeC` (핑퐁) | C_E, C_N, C_NE, C_SE | 간선은 E, N, NE, SE 네 방향을 한 장에 |
| `aux` | 우변, 차폐 항 M, 인접 최대 전도도, 관 두께 | 쉬는 두께 패스가 쓰고 마름·젖음이 다시 읽는다 |
| `edgeW` | W 네 방향 | 멀티그리드의 레벨 0 가중치 |
| 정적 | 간선 잡음 G(4), 새 간선 전도도(4), (η, 유인장 c) | 초기화 때 한 번 올린다 |
| 멀티그리드 레벨 l | W_l(4), (우변, M), p(핑퐁), 잔차 | 192²: 7단, 384²·512²: 8단, 768²: 9단 |

- 이웃 접근은 `texelFetch` 와 정수 나머지로 한다(토러스). 필터링은 쓰지 않는다.
- 새 간선 판정은 저장된 전도도가 0 인지로 한다(활성 간선의 전도도는 0 이 되지 않으므로 numpy 의 "직전 스텝에 비활성"과 같다).

### 패스 구성 (한 스텝, 기준형)

| 순서 | 패스 | 하는 일 | 드로콜 |
|---|---|---|---|
| 1 | `edge_activate` | 새 간선에 초기 전도도, 비활성 간선은 0 | 1 |
| 2 | `phase` ×4 | 규칙 1. 부분 스텝 4회 | 4 |
| 3 | `rest` (다중 타깃) | 규칙 2. 쉬는 두께(θ_eff = θ + ψ), 우변, M, 관 두께 → `aux`. 간선 가중치 → `edgeW` | 1 |
| 4 | `mg_init` | 웜스타트 p₀ = p + 0.5·(p − 직전 p) | 1 |
| 5 | `mg_coarsen` ×(L−1) | 조대 연산자: 가중치 /1.5, 차폐 항은 자식 합 | L−1 |
| 6 | V 사이클 ×ncyc | 레벨마다 앞 스무딩 2, 잔차, 제한, (재귀), 보간, 뒤 스무딩 2. 최조 격자 Jacobi 4회. 대각은 스무더가 가중치에서 바로 계산 | ncyc·(7(L−1)+4) |
| 7 | `flux` (다중 타깃) | 규칙 4. h 갱신, age·sage 증가, p 저장 | 1 |
| 8 | `reduce` ×3 | 규칙 5의 Q0: 8×8 블록 합으로 전역 평균. 같이 최소 두께·최대 전도도 | 3 |
| 9 | `reinforce` | 규칙 5. 전도도 갱신 | 1 |
| 10 | `dry_mark`, `dry_confirm`, `dry_share`, `dry_apply` | 규칙 6. 막다른 끝 판정(연결수), 2×2 색 차례, 음수 셀, 부피를 이웃 두께에 비례해 나눔 | 4 |
| 11 | `blur13` ×2 | 젖은 마스크의 가우스 흐림(σ=2, 반경 6) | 2 |
| 12 | `wet_mark`, `wet_apply` (다중 타깃) | 규칙 7. 후보와 공급 셀 선택, 부피 이전, θ·p 물려받기 | 2 |

기준형의 예상 드로콜(2사이클): 192² 118, 384²·512² 133, 768² 148. spec 의 추정(137~153)과 같은 범위다.
Step 7 에서 "잔차+제한", "보간+첫 뒤 스무딩"을 한 패스씩으로 합치면 레벨당 7 → 5 가 되어 192² 94, 384²·512² 105, 768² 116 이 된다.

### 기준 자료와 잡음
- 정적 잡음은 numpy 와 JS 가 같은 정수 해시(lowbias32)와 Box–Muller 로 만든다. 잡음 파일을 주고받지 않고도 두 쪽의 초기 조건이 같아진다.
  기준 모델의 난수가 `np.random.default_rng` 에서 이것으로 바뀌므로 기준 실행은 새로 돌린다.
- 기준 모델의 설정은 5차 검증에 쓴 "굶은 이주"와 같되 마름의 부피 나눔만 spec 대로 "두께 비례"로 둔다.
- numpy 가 내보내는 것 (float32, gzip): ① 풀이 재생용 상태 — 간선 가중치, 차폐 항, 우변, 웜스타트, 1·2·3사이클 뒤의 p, 직접 풀이의 p. 192² 세 시점과 384² 한 시점.
  ② 스텝 일치용 — 192² 의 t=200 전체 상태와 그 1, 10스텝 뒤 상태. 초기 상태에서 1, 10, 50스텝 뒤 상태.
  ③ A1·A2 기준 — 직접 풀이와 멀티그리드로 돌린 192²·384² 실행의 요약(무게중심 궤적, 최대 전도도, 유량 오차).
- 브라우저는 `DecompressionStream` 으로 푼다.

## 구현 단계

### Step 0: 준비
- 작업 브랜치는 이 세션에 지정된 `ccr-0f17b913-m1k02r` 를 쓴다. 이 계획 문서를 먼저 커밋한다.
- `main` 병합은 Step 9 에서 주 세션이 한다(사용자 지시).

### Step 1: numpy 기준 자료
- `ref_model.py`: h1.py 사본에 해시 잡음 옵션과 내보내기 훅을 더한다. 동역학은 바꾸지 않는다.
- `export_ref.py`: 위 ①②③을 만들어 `public/stage0/ref/` 와 `specs/plasmodium-core/stage0/ref/` 에 쓴다.
- 파일: `specs/plasmodium-core/stage0/ref/*`, `public/stage0/ref/*`
- 확인: 옵션을 끄면 h1.py 와 최종 배열이 같다. 해시 잡음으로 돌린 굶은 이주의 이동 거리와 목표 도달 시각이 5차 기준 실행의 범위(이동 63~76셀, 도달 221~237) 안이다. 자료 합계 3 MB 이하.

### Step 2: 페이지 뼈대와 GL 도우미
- `stage0.html`, `vite.config.ts` 다중 페이지, `src/config.ts` 의 `PLASM`, `glx.ts`, `params.ts`, `hashNoise.ts`, `main.ts` 뼈대.
- 페이지가 WebGL2, `EXT_color_buffer_float`, 다중 타깃 수, 타이머 질의 지원 여부를 적는다. 지원하지 않으면 그 사실만 보여 주고 멈춘다.
- 캔버스 하나에는 WebGL2 컨텍스트만 만든다. 글자는 DOM 에 쓴다.
- 확인: `npm run build` 통과. 헤드리스에서 `stage0.html` 이 지원 항목을 보고한다. JS 해시 잡음이 numpy 값과 같다(표본 1000개, 차이 1e-6 이하).

### Step 3: 멀티그리드와 A0 (재생 시험)
- `MultigridGPU.ts` 와 `mg_*.glsl` 을 mgt.py 와 같은 순서로 옮긴다(기준형).
- `tests.ts` 의 A0: 재생용 상태를 텍스처에 넣고 1·2·3사이클을 돌려 p 를 읽는다.
- 의존: Step 1, Step 2
- **A0 통과 기준**: 네 상태 모두에서 ① GPU 의 p 와 numpy 멀티그리드의 p 의 상대 차이(L2)가 1e-3 이하, ② 직접 풀이 대비 유량 오차가 numpy 값과 ±0.01 안(1·2·3사이클 각각).

### Step 4: CPU 기준 풀이
- `cpuSolver.ts`: 젖은 셀 위의 9점 연산자를 행렬 없이 푸는 켤레기울기(Jacobi 선조건, float64, 상대 잔차 1e-10).
- spec 의 "CPU 직접 풀이" 자리에 이것을 쓴다. 직접 분해와 같다는 것은 재생용 상태에서 numpy 직접 풀이의 p 와 견줘 확인한다.
- 의존: Step 1, Step 2
- 확인: 네 상태에서 numpy 직접 풀이와 상대 차이 1e-6 이하. 젖은 셀 5만 개(768² 의 몸 크기)짜리 합성 상태를 한 번 푸는 데 10초 이하.

### Step 5: 모델 패스와 스텝 일치 시험
- `PlasmGPU.ts` 와 규칙 1~7 의 셰이더. 위 "패스 구성" 순서 그대로.
- 틀리기 쉬운 곳을 numpy 와 글자 그대로 맞춘다: 젖음의 공급 셀 선택 순서(E, N, NE, SE, W, S, SW, NW 에서 처음으로 더 큰 것), 가우스 핵(반경 6, 감김),
  마름의 연결수와 색 차례, "남는 이웃이 없으면 마르지 않는다"의 두 번 판정, 새 셀이 공급 셀의 θ 와 p 를 물려받는 것, 인접 최대 전도도를 강화 전 값으로 쓰는 것.
- 스텝 일치 시험: numpy 상태를 넣고 GPU 로 1, 10스텝 돌려 numpy 의 다음 상태와 견준다.
- 의존: Step 3
- **통과 기준**: 1스텝 뒤 젖은 마스크가 같고 h 의 최대 차이 1e-3 이하, θ·C 의 상대 차이 중앙 1e-4 이하. 10스텝 뒤 젖은 마스크가 다른 셀이 몸의 0.5% 이하. 초기 상태에서 50스텝 뒤 총 부피의 상대 오차 1e-5 이하.
  기준을 넘으면 기준을 고치지 않고 원인을 찾는다(패스별로 numpy 중간값과 견주는 모드를 둔다). 1스텝 뒤 마스크가 다른 셀이 있으면 그 셀의 판정 여유가 float32 반올림 크기인지 확인해 적는다.

### Step 6: 시험 러너와 A1·A2
- `run_stage0.cjs`: 빌드한 페이지를 헤드리스 Chromium 으로 열어 `?test=…` 모드를 돌리고 결과 JSON 을 `specs/plasmodium-core/stage0/results/` 에 쓴다. 화면 갈무리는 `screenshots/` 에 둔다.
- 시험 모드에서는 매 스텝 1×1 통계 텍셀(스텝 안 최소 두께, 최대 전도도)과 스텝 끝 통계(음수 셀 수)를 읽고, 200스텝마다 전체 상태를 읽어 CPU 기준 풀이로 유량 오차를 낸다. 무게중심은 읽은 h 에서 토러스 최소 상으로 추적한다.
- 실행 (이 컨테이너의 소프트웨어 렌더러 기준 예상 시간)

  | 격자 | 시드 | 사이클 | 위상 무늬 | 스텝 | 예상 시간 |
  |---|---|---|---|---|---|
  | 192² | 2개 | 2 | 없음 | 1만 | 각 11분 |
  | 192² | 1개 | 3 | 없음 | 1만 | 11분 |
  | 192² | 1개 | 2 | 삼각 격자 | 1만 | 11분 |
  | 384² | 2개 | 2 | 없음 | 1만 | 각 41분 |
  | 512², 768² | 1개 | 2 | 없음 | 2천 | 14분, 약 30분 (NaN·음수만 본다) |

- 의존: Step 4, Step 5
- **A1 통과 기준** (192²와 384²의 2사이클·무늬 없음 실행 4개): NaN 없음, 스텝 끝 음수 두께 셀 0, 실행 중 최대 전도도가 같은 시드의 numpy 멀티그리드 실행의 3배 이내.
- **A2 통과 기준** (같은 4개): 50스텝마다 잰 유량 오차의 중앙값 ≤ 0.15, 99백분위 ≤ 0.4. t=0~400 의 무게중심 이동 거리와 유인원에 닿는 시각이 같은 시드의 numpy 직접 풀이 실행의 ±10% 안.
  (GPU 긴 실행을 돌리기 전에 고친 것: 처음에는 t=100~300 의 이동 거리로 정했는데, 기준 실행을 만들어 보니 numpy 의 멀티그리드 실행조차 같은 시드의 직접 풀이 실행과 이 값이 7~12% 달랐다(29.0 대 33.0, 31.4 대 33.9). 닿는 시각 전후에 걸친 창이라 궤적의 작은 차이에 민감하다.
  t=0~400 의 거리는 2~3%, 닿는 시각은 0~3% 차이다. t=100~300 의 값도 함께 적는다. 유량 오차는 spec 의 200스텝보다 촘촘히 재어 99백분위가 뜻을 갖게 했다.)
- 3사이클과 삼각 격자 실행은 같은 수치를 기록만 한다(spec: "2사이클과 3사이클을 둘 다 잰다").

### Step 7: 스텝을 싸게 만들기
결과를 바꾸지 않는 것부터 한다. 각각 끄고 켤 수 있게 두어 벤치마크가 따로 잰다.

| 수단 | 내용 | 기대 |
|---|---|---|
| (a) 몸 주변만 계산 | 모든 패스에 몸의 경계 상자(여유 8셀 + 갱신 주기)만 그리는 가위 사각형을 건다. 멀티그리드의 각 레벨도 같은 비율로. 경계 상자는 GPU 축소 패스로 구해 비동기로 읽는다(멈춤 없음). 상자가 격자 가장자리를 넘으면 전체를 그린다 | 채우기 비용이 격자 크기가 아니라 몸 크기를 따른다. 512² 에서 지름 100셀인 몸이면 약 1/15 |
| (b) 멀티그리드 패스 합치기 | "잔차+제한", "보간+첫 뒤 스무딩"을 한 패스씩으로. 산술은 같다 | 레벨당 7 → 5. 512² 에서 133 → 105 드로콜 |
| (c) 작은 패스 합치기 | `dry_mark`+`dry_confirm`, `edge_activate` 를 뒤 패스에 접기. 조대 레벨(32² 이하)의 스무딩 2회를 넓은 스텐실 한 패스로 | 드로콜 약 20개 더 줄임 |
| (d) 텍스처 형식 줄이기 | p·잔차는 R32F, (우변, M)은 RG32F | 메모리 대역폭 감소 |

- (a)는 가위 밖이 변하지 않는 마른 영역이라 결과가 같다. 여유 폭이 그것을 보장하는지 스텝 일치 시험으로 확인한다.
- 의존: Step 6
- 확인: 각 수단을 켠 채 A0 와 스텝 일치 시험을 다시 통과. (b)만 켰을 때 드로콜이 192² 94, 512² 105, 768² 116.

### Step 7b: 시간 간격 키우기 (numpy)
- 한 스텝이 나아가는 모델 시간을 2배, 4배로 키워도 결과가 유지되는지 본다(dt 0.1 → 0.2, 0.4. 위상의 부분 스텝은 같은 간격이 되게 늘린다). 유지되면 같은 비용으로 화면 속도가 그만큼 빨라진다.
- 5차의 기준 시험 둘(굶은 이주, 대칭 먹이 셋 + 삼각 격자)을 시드 21~26 으로 돌려 5차의 dt=0.1 값과 견준다.
- 파일: `specs/plasmodium-core/research/round6/` (보고와 코드)
- 의존: 없음 (Step 1~6 과 나란히 돌린다)
- **통과 기준** (dt 마다): 이주 중 정맥 최대 성분 0.8 이상인 시드와 굵은 관으로 이어진 쌍의 수가 dt=0.1 의 값에서 1개 넘게 줄지 않고, 몸이 갈라진 실행이 늘지 않으며, 스텝 끝 음수 두께가 늘지 않고, 멀티그리드 유량 오차의 중앙값이 0.15 이하.
  통과한 가장 큰 dt 를 GPU 쪽 A1·A2 에서 한 번 더 확인한 뒤 벤치마크에 넣는다. 작성자 혼자 낸 결과이므로 채택 전에 독립 검증을 받는다.

## 화면 속도와 비용의 관계

모델에서 맥동 한 주기는 40스텝이고 전진 속도는 스텝당 약 0.02셀이다(dt=0.1). 지도 1500px 에 384² 격자면 1셀이 3.9px 이다.
맥동 주기와 전진 속도의 비는 모델(과 실제 점균)에 묶여 있어 따로 고를 수 없다.

| 프레임당 스텝 (60fps) | 화면의 맥동 주기 | 화면의 전진 속도 (384² / 512²) | 300px 떨어진 먹이까지 | 스텝당 허용 시간 |
|---|---|---|---|---|
| 0.25 | 2.7초 | 1.2 / 0.9 px/s | 약 4분 | 16ms |
| 1 | 0.67초 | 4.7 / 3.5 px/s | 약 1분 | 4ms |
| 3 | 0.22초 | 14 / 11 px/s | 약 20초 | 1.3ms |

지금 게임의 에이전트는 프레임당 1px(초당 60px)을 간다. 블롭 전진면의 실제 속도는 재지 않았지만 표의 어느 줄보다 빠를 가능성이 크다.
사용자 결정이 "최대한 빠르게"이므로 목표는 표의 아래쪽이다. 수단은 둘이다: 스텝을 싸게 만들기(Step 7), 한 스텝이 나아가는 시간을 키우기(Step 7b. dt 를 4배로 하면 표의 속도가 4배가 된다).

## 위험 요소

- **지금 게임만큼 빠르게는 안 될 수 있다.** 스텝당 드로콜이 100개 안팎이라 드로콜마다 드는 고정 비용만으로 1~2ms 가 될 수 있고, 채우기 비용도 격자 전체를 그리면 크다(512² 에서 스텝당 텍셀 읽기 약 1억 회). Step 7 과 7b 가 이것을 줄이는 수단이다. 얼마나 빨라지는지는 재 봐야 안다.
- **이 컨테이너에서는 실제 GPU 시간을 잴 수 없다.** GPU 가 없고 연결된 사용자 컴퓨터도 없다. A0~A2 와 드로콜 수는 여기서 끝내고, 시간은 사용자가 배포된 페이지를 한 번 열어 재야 한다.
- **시간 간격을 키우는 것은 모델을 바꾸는 일이다.** numpy 에서 기준 시험을 통과하고 독립 검증을 받은 뒤에만 쓴다. 통과하지 못하면 dt=0.1 로 둔다.
- **몸 주변만 계산하는 것은 토러스 가장자리에서 깨진다.** 0단계에서는 상자가 가장자리를 넘으면 전체를 그리는 것으로 피한다. 몸을 따라 움직이는 창으로 바꾸는 것은 1단계의 일이다.
- **float32.** numpy 기준은 float64 다. 384² 에서 float32 로 유량 오차가 같았다는 검증자 실행이 한 번 있을 뿐이다. 문턱 비교(마름, 젖음)가 반올림으로 갈려 궤적이 갈라지므로 긴 실행은 통계로만 견준다.
- **반정밀도만 되는 기기.** `EXT_color_buffer_float` 가 없는 기기(일부 모바일)에서는 돌지 않는다. 페이지가 이를 보고하게만 하고 대응은 범위 밖으로 둔다.
- **마름과 젖음의 모으기 패스.** numpy 에서는 흩뿌리기(공급 셀에서 빼기)인 연산을 GPU 에서는 모으기로 바꾼다. 스텝 일치 시험이 이것을 잡도록 t=200 의 성숙한 상태(마름과 젖음이 모두 일어나는 시점)를 쓴다.
- **기준 자료가 저장소에 들어간다** (압축 3 MB 이하). 배포물에도 실린다.
- **긴 실행 시간.** 384² 1만 스텝이 소프트웨어 렌더러로 40분쯤 든다. 백그라운드로 돌린다.
- **삼각 격자의 주기.** 192²·384²·768² 는 96 의 배수라 주기 96 을 쓸 수 있지만 512² 는 아니다(64 또는 128). 관문 A 에서는 192²·384² 에서만 켠다.
