## 규칙 8의 구현

| 상태 | 텍스처 | 내용 |
|---|---|---|
| 먹이 상태 | 먹이 수 × 1, RGBA32F, 핑퐁 | 남은 양, 유인장의 세기, 다 떨어진 스텝, 이번 스텝에 셀 하나가 받는 두께 |
| 저장 배율 | 격자 크기, RG32F, 핑퐁 | H, 직전 스텝의 쉬는 두께(맥동을 뺀 값. 90% 조건이 이것과 견준다) |
| 정적 | 격자 크기 RG32F / RGBA32F 1~2장 / 먹이 수 × 1 | 셀이 든 먹이 원반의 번호, 먹이별 가우스 유인장(8개까지), 원반을 훑는 창의 가운데 |

한 스텝의 순서는 numpy와 같다: 쉬는 두께 패스가 **직전 스텝의** 먹이 상태로 H를 갱신하고 → 압력 풀이 → 먹이 패스가 스텝 시작 시점의 젖은 마스크로 먹는 양을 정하고
→ 유량 패스가 먹은 만큼 두께를 더하고 살아 있는 먹이 위의 셀은 늙지 않게 하고 → 젖음 패스가 먹은 뒤의 세기로 유인장을 낸다.

- **패스는 하나 는다**(먹이 패스. 타깃이 먹이 수 × 1텍셀이다). 쉬는 두께 패스의 출력이 두 장에서 세 장이 된다. CPU로 읽어 오는 값 없이 GPU 안에서만 돈다.
  스텝당 드로콜: 기준형 119, 합친 패스 95, 합친 패스 + 몸 주변만 95, + 두 번 스무딩 71 (관문 A는 118 / 94 / 94 / 70).
- **먹지 않는 설정은 그대로다.** 관문 A의 굶은 이주(유인원 하나, 먹지 않음)에서는 먹이 패스가 돌지 않고 셰이더의 계산식도 예전과 같다(`#if` 분기).
  고치기 전후의 빌드로 짧은 실행 셋(192² 1500스텝과 600스텝, 384² 800스텝)을 돌려 기록한 값(궤적, 유량 오차 수열, 최대 전도도, 드로콜 수)이 모두 같았고,
  A0와 관문 A의 스텝 일치 시험의 수치도 저장된 결과와 같다.
- **먹은 양은 "남은 양에서 실제로 빠진 만큼"으로 준다.** float32에서는 남은 양 1200에서 0.4를 빼면 반올림 때문에 0.4와 조금 다른 양이 빠진다.
  몸에 더하는 양을 그 차이로 계산하므로 먹이에서 뺀 양과 몸에 더한 양이 어긋나지 않는다(먹이 실행의 부피 오차 3e-5 이하).
- **numpy와 정의가 다른 것 하나**: "스텝 안 최소 두께"를 GPU는 먹은 양을 더한 뒤에 잰다(numpy는 더하기 전). 먹이 원반의 셀에서만 다르고 판정에는 쓰지 않는다.
- 먹이는 8개까지, 원반이 서로 겹치면 오류를 낸다. 먹이의 자리는 시뮬레이션을 만들 때 정해진다(게임에서 먹이가 생기고 사라지게 하려면 이 부분을 다시 짜야 한다. "남은 것").

## 먹이가 있는 스텝 일치

numpy가 저장한 상태(셀 상태 + H + 먹이 상태)에서 출발해 GPU로 돌린 뒤 numpy의 뒤 상태와 견줬다(192², 시드 1, 위상 무늬 (나)).
설정은 셋이다: 대칭 먹이 셋(닿기 직전 · 먹는 중 · 첫 먹이가 떨어지기 7스텝 전), 줄지 않는 먹이 여섯(유인장의 둘째 텍스처와 "줄지 않는 먹이를 먹는" 길),
금방 떨어지는 먹이 셋(유인장의 세기가 1e-4 아래에서 멈춘 뒤까지).

|---|---|---|---|---|---|---|---|
| 먹이 셋 · 스텝 580 | 1 / 10 / 50스텝 | 0 / 0 / 0 (2763~2921셀) | 3.5e-4 / 4.8e-4 / 4.7e-4 | 0 / 4.1e-9 / 2.8e-7 | 같음 | 0 / 0 / 1.2e-7 | 3.8e-6 / 1.5e-5 / 7.6e-5 |

- 먹이가 다 떨어진 스텝은 모든 시점에서 numpy와 같다. 금방 떨어지는 설정의 120스텝 뒤에는 세 먹이의 세기가 0.00552(사라지는 중) / 1(살아 있음) / 9.14e-5(1e-4 아래에서 멈춤)로 numpy와 같다.
- 판정은 1스텝 뒤(마스크 완전 일치, 두께 ≤ 1e-3, 위상·전도도 중앙 ≤ 1e-4, 남은 양 ≤ 1e-5, H ≤ 1e-5, 나이 ≤ 2e-3)와 10스텝 뒤(불일치 ≤ 0.5%)로 하고, 그 뒤는 기록만 한다.

- 계산 방식 다섯 가지(기준형, 합친 패스, 몸 주변만, 두 번 스무딩)가 모두 통과했고, 넷은 기준형과 두께가 비트 단위로 같다(최대 차이 0).

## 판정 도구와 그 확인

GPU 실행과 numpy 실행을 **같은 채점기**로 채점한다. 그러려고 GPU 실행을 numpy 실행과 같은 꼴의 파일로 바꾼다.

1. 시험 페이지(`?test=b&scn=…&dump=1`)가 시나리오를 돌리며 모델 시간 20마다 상태(전도도, 젖음, 두께, 나이, 위상, 구간 통계)를 러너로 보낸다(한 장 3.4MB, 평면 23개).
2. 구간 통계는 시험용 패스 하나가 GPU 안에서 쌓는다: 맥동 한 주기(40스텝)의 두께 평균·진폭, 다섯 주기(200스텝)의 간선별 순유량·총유량·평균 전도도. numpy 기준 모델과 같은 구간, 같은 시점이다.
3. 변환기(`metrics/gpu2run.py`)가 numpy 실행 폴더와 같은 이름·같은 꼴의 파일로 바꾼다. 채점기(`metrics/bmet.py`)는 어느 쪽 폴더든 같은 코드로 읽는다.
4. 정맥·먹이 연결의 지표는 5차 검증자의 `vmet.py`(사본)와 3~5차의 `graphm.py`를 그대로 쓴다.

확인한 것:

- **넣은 그대로 나온다.** numpy 상태(대칭 먹이 셋, 스텝 2000)를 GPU에 넣고 바로 내보낸 덤프가 넣은 값과 비트 단위로 같다(전도도, 젖음, 두께, 나이, 위상).
- **구간 통계가 numpy와 맞는다.** 같은 상태에서 201스텝을 돌려 얻은 구간(스텝 2000~2199)을 numpy의 같은 구간과 견주면 상대 차이(L2)가
  총유량 9.5e-5, 순유량 7.1e-5, 평균 전도도 3.0e-5, 두께 평균 3.5e-6, 두께 진폭 1.8e-4이고 젖은 마스크는 4497셀이 모두 같다(`metrics/check_dump.py`).
- **처음 상태에서 1000스텝**을 돌린 GPU 실행은 numpy와 먹이에 닿는 시각 셋이 같고(64.9 / 75.8 / 58.9) t=60까지 젖은 마스크가 같다.
- **위상 지연의 재는 법**: 2차 E10은 누적된 위상으로 쟀는데 GPU의 위상은 0~2π로 감겨 있다. 맨 앞 셀에서 젖은 이웃을 따라 위상을 풀어 쓰는 방법으로 바꿨고,
  numpy 실행에서 두 방법의 값이 소수 셋째 자리까지 같다(0.433~1.424바퀴).
- **4~5차 검증의 숫자가 다시 나온다.** 대칭 먹이 셋(numpy, 시드 12개)의 굵은 쌍이 34/36이다(5차 검증: 52/54). 굶은 이주의 그 순간 전도도로 잰 정맥 최대 성분이 0.85~0.90이다(5차: 0.8 이상이 16/18).

지표의 정의는 실행하기 전에 `metrics/bmet.py`의 머리말에 적었다. spec의 문장을 숫자로 옮기면서 정한 것:

| 기준 | spec의 문장 | 이렇게 쟀다 |
|---|---|---|
| B2 | 한 방향 이주 | 무게중심 이동(t=0~300) ≥ 20셀이고 유인원 방향과의 각 ≤ 30° |
| B3 | 시간 평균한 전도도 | 직전 다섯 주기(200스텝)의 평균. 정맥 = 평균 전도도 > 4인 간선. t ≥ 200의 저장 시각마다 재서 중앙값 |
| B3 | 전진면에서 멀수록 굵음 | 전진면에서 먼 절반의 정맥 전도도 중앙 ÷ 가까운 절반의 중앙 > 1, 거리와 log 전도도의 순위 상관 > 0 |

## GPU와 numpy가 다르게 나온 줄

미리 정한 규칙(넘은 수 차이 ≤ 1, GPU 중앙값이 numpy 시드 범위 ±5% 안)으로 판정한 49줄 가운데 "다름"이 나온 줄은 넷이다: B4의 정맥 총유량/순유량, B7의 끝 넓이·젖음이 바뀌는 비율·B3을 채운 구간의 비율.
B7의 셋은 위에서 본 대로 시드 2개의 범위가 좁아서였고, 시드를 5개로 늘리면 여섯 값 모두 GPU의 중앙이 numpy의 범위 안이다. 여기서는 총유량/순유량을 따진다.

**무엇이 보였나.** 판정에 쓴 시드 5개에서 GPU가 다섯 번 모두 높았다(3.81 / 4.05 / 4.18 / 3.69 / 4.23 대 3.65 / 3.64 / 3.78 / 3.38 / 3.81. 차이 +0.15~+0.42).
구현의 차이라면 찾아야 하는 것이다.

**재는 길은 맞다.** 같은 상태에서 출발하면 GPU의 구간 통계는 numpy와 1e-4 안에서 같다("판정 도구와 그 확인"). 굶은 이주 실행에서도 궤적이 겹치는 동안은 정맥의 총유량·순유량이 같고(시드 2·3은 t=120까지 GPU/numpy 비가 1.000. 시드 1은 t=100에 이미 순유량이 3% 다르다),

  세 묶음(저장만, 풀이까지, GPU)이 같은 부호로 나온 것과, 따로 본 지속 실행(t ≥ 400의 저장 상태 81장씩, 5 대 5)에서도 GPU의 정맥 순유량이 numpy의 0.97배(t = −1.6)인 것이 근거다.
- 게임은 float32로 돈다. numpy(float64)의 수치를 기준으로 쓸 때 **1~3%의 이 차이는 구현 오차가 아니라고 알고 있으면 된다.**

## 90% 조건 (`res_gate`)

## 256² 격자와 무늬의 주기

관문 A의 휴대폰 측정에서 256²가 384²보다 스텝이 절반 이하로 싸서 게임 격자의 후보가 됐다. 무늬 (나)의 주기 96은 256의 약수가 아니어서 **주기 128**을 넣어 봤다(시험한 적이 없는 값이었다).

- **판정 스크립트: 구멍을 찾았다.** NaN으로 멈춘 실행이나 비어 있는 값, 빠진 시드가 "통과"로 세어질 수 있었다(예: 닿지 못한 방향이 있는 시드를 비율 목록에서 빼면 나머지만으로 통과가 된다).
  고쳤다: 판정에 쓰는 시드를 표로 정해 두고, 없는 실행·끝까지 돌지 못한 실행·빈 값은 "없음"(불통과)으로 센다. 이번 실행들에는 그런 경우가 없어서 결과는 달라지지 않았다.
- 그 밖에 고친 것: 새로 젖은 셀을 세는 법을 양쪽에서 같게(스텝 끝 마스크의 차이), 새로 젖은 셀이 100개 미만이면 비율을 내지 않게, 변환기가 그 실행의 덤프만 바꾸게,
  스텝 일치 시험에 나이·노화 나이·유인장 세기를 넣고 시험이 지나지 않던 길 둘(먹이 여섯, 유인장이 멈춘 뒤)을 더했다.
- 검토자가 짚었고 **고치지 않은 것**: B4의 위상 지연 판정이 고른 시각에 달려 있다(위에 적었다). "같은가" 규칙이 시드가 적은 줄에서 우연히 "다름"을 낼 확률이 높다(위에서 시드를 늘려 확인했다).
  러너의 POST에 크기 제한과 출처 확인이 없다(127.0.0.1의 임의 포트에서만 듣는다).

## 계획과 달라진 것

- **Step 9(위상 무늬 (가) 수축파)는 하지 않았다.** 선택 항목이었고, 판정은 계획대로 (나)로 했다.
- 시나리오 `mig2x`(몸 2배)를 더했다(B4의 "몸 길이를 2배로"를 한 실행 안에서는 볼 수 없어서).
- 판정 뒤에 더한 실행: 굶은 이주의 시드 6~15(양쪽), 지속 실행의 시드 3~5(양쪽), float32 대조 실험(numpy 15개씩 두 가지). 모두 "같은가"가 "다름"으로 나온 줄을 따지려는 것이고 판정표에는 넣지 않았다.
- "같은가" 규칙에 ±5%의 여유를 넣었다(실행 전). 판정 스크립트를 검토 뒤에 고쳤다(위).
- 먹이 설정의 꼴: 먹이마다 폭·진폭·반지름·양을 따로 두지 않고 numpy처럼 공통 값이다. 상수 묶음의 이름은 `PLASM_FOOD`다(`FOOD`는 지금 게임이 쓰고 있다).
- 스텝 일치 덤프의 셋째 시점은 "첫 먹이가 떨어진 직후"가 아니라 "떨어지기 7스텝 전"이다(떨어지는 순간이 시험 구간 안에 들게).

## 남은 것

- **모델의 숙제 넷**(위의 표): 외딴 음수 셀, 방향별 도달 시각, 먹이 넷의 긴 배치, 오래 가면 갈라지는 몸. spec의 "미해결 문제"에 옮겼다.
- **B5의 축소안을 정해야 한다.** spec은 B5가 실패하면 "가까운 먹이끼리만 관을 보장"하는 축소안을 검토한다고 적었다. 대칭·비대칭 먹이 셋(거리 35~45)은 되고 거리 75의 먹이가 낀 배치는 안 된다.
- **먹이가 생기고 사라지는 게임의 먹이**는 지금 구조(먹이의 자리가 만들 때 정해지고 먹이별 유인장이 정적 텍스처)로는 안 된다. 1단계에서 먹이 목록을 CPU가 고칠 수 있는 텍스처로 바꾸고 유인장을 그때그때 다시 그려야 한다.
- **실제 GPU에서의 산술**은 이번에도 확인하지 않았다(소프트웨어 렌더러에서만 돌렸다). 시험 페이지의 "먹이 셋"을 휴대폰에서 눈으로 볼 수 있다.
- 규칙 8을 켠 스텝의 **휴대폰 시간**은 아직 재지 않았다(속도 측정에 "먹이 셋" 줄을 넣었다. 다음 측정에서 나온다).
- 위상 무늬 (가)는 GPU로 옮기지 않았다. B8(입자층)은 하지 않았다.

## 다시 돌리는 법

```bash
npm run build
cd specs/plasmodium-core/stage0

# 먹이 스텝 일치, 판정 도구의 확인
node run_stage0.cjs parityfood "test=parityfood"
node run_stage0.cjs bstats "test=bstats" && python3 metrics/check_dump.py     # ref/runs/b_food3_s1 이 있어야 한다

# 실행 전부 (GPU 약 2시간, numpy 약 1시간. 3개씩 나란히)
bash ref/run_b_ref.sh                                   # numpy → ref/runs/b_*
bash run_b.sh                                           # GPU → runs_gpu/b_* 와 results/b/gpu_*.json
python3 metrics/bmet.py ref/runs/b_* --out results/b    # numpy 채점 → results/b/numpy_*.json

# 판정과 이 문서
python3 judge_b.py
python3 make_result_b.py                                # RESULT-B.tmpl.md → RESULT-B.md, results/b_judge.txt

# 시나리오 하나만 (덤프 없이 요약만 보려면 dump=1 을 뺀다)
node run_stage0.cjs b_food3_s1 "test=b&scn=food3&seed=1&dump=1&name=b_food3_s1"
```

- 기준 상태 덤프(스텝 일치용)는 `ref/export_ref.py dumpsfood 580 2000 3790`, `dumpsfood2 six 500`, `dumpsfood2 fade 786`으로 만든다(`public/stage0/ref/`).
- numpy 실행을 여럿 나란히 돌릴 때는 스레드 수를 1로 묶어야 한다(`NUMBA_NUM_THREADS=1`. `export_ref.py`가 기본으로 넣는다). 안 그러면 한 스텝이 80배까지 느려진다.
- 상태 덤프(`dumps/`)와 변환한 실행(`runs_gpu/`), numpy 실행(`ref/runs/`)은 커서 저장소에 넣지 않는다. 채점 요약(`results/b/`)과 실행 요약(`results/b_*.json`)만 넣는다.
